# 60条工作流候选集：运行前内部审查

## 结论

**暂不冻结、不启动180次正式运行。** Fixture能构造不等于验收有效。
本次仅审查数据/实现/评分契约，没有运行真实模型、没有改变业务代码、没有按模型输出调整标签。
这不是教师独立审核，也不是Blind Holdout。

## 已核实的公共问题

1. **供给差异**：`tests/evals/fixtures/paper.py:seed_success_question_bank`只在第一章放入4选择、3填空、5计算、2证明，共14题，难度均为3；第三章为0。已有卷Fixture另有按题型的难度2/3/4替换候选。第三章用例可测试方案保留，但不能当作可完成生成的正例。第一章6计算也必然短缺。
2. **Paper不变检查存在盲区**：`runner.py:_paper_db_snapshot`只读传入的原Paper ID，无ID返回None。新建场景可能永远比较None与None；已有卷即使错误创建新版本，旧Paper也可能不变。因此不能把`paper_unchanged`等同于“未生成/未修改数据库”。需要隔离库的Paper/版本/Item全集以及活跃版本指针前后比较。
3. **仅检查最后一轮**：Runner记录turns，但`actual['before']`是最后一轮之前；现有grader主要评最后一轮。短缺Case第一轮自动生成、第二轮澄清可能漏检。需要逐轮禁止确认和状态差异检查。
4. **Tool名字不等于成功**：`acceptance_grader.py`的required_tools只检查调用名称，不检查Observation.ok或产物是否存在。伪造一个失败read/preview Tool，状态标为completed/waiting_confirmation，也可能通过。
5. **回复内容没验证**：咨询类仅completed、禁用部分Tool、存在Trace就能通过；读卷未验证实际题量/题干，澄清未验证问题非空。故目前只能称workflow boundary检查，不能称内容正确率。
6. **没有成功确认闭环**：Pending组10条实际是6修改+4取消，没有成功Confirm；版本操作只有缺失目标的拒绝例。不得称覆盖全部确认/恢复流程。
7. **样本重复较多**：多数组卷为题量/分值变体，4条取消近义。可以作为回归，不等价于60种独立业务能力；适合后续替换部分冗余项而非继续扩数量。

## 最小修正顺序

1. 先与用户确认待人工项；不要用‘实际模型输出是什么’来决定正确标签。
2. 为测试Runner增加隔离库全集状态快照、逐轮契约；不改Domain Service。
3. 强化grader：成功Observation、实际产物、有效澄清问题、题型/范围/未变字段。
4. 为grader写正反例测试：正确行为通过，失败Tool、假产物、自动确认、早期越界必失败。
5. 再选6条已审核场景冒烟；修复评测问题后才能冻结正式Candidate基线。

当前仅完成审查，未宣称60条已具备正式评分资格。现有数据保留原样以便复核。
