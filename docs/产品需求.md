# Teacher Agent Business Contract

## 1. 产品定位

* Tutor 是面向教师的教学助手。
* 不是单纯组卷工具。
* 不是学生管理系统。
* 不保存学生长期档案。
* 当前按本地单用户系统设计，不考虑多租户、共享题库、复杂权限体系。

---

# 2. Conversation

## 2.1 Conversation 职责

Conversation 用于：

* 保存用户与 Agent 的交流历史。
* 恢复当前对话上下文。

Conversation 不是业务事实来源。

业务状态必须由 Domain Entity 保存：

* TeachingDesign
* Paper
* Generation
* Question Snapshot

---

## 2.2 Conversation 历史

所有 Conversation 都进入历史列表，包括：

* 教学咨询
* 教学设计
* 组卷任务
* 试卷修改

系统不能自动处理会话：

* 不自动删除。
* 不自动归档。
* 不自动合并。
* 不自动判断重要性。

历史名称使用内容摘要，而不是第一条用户消息。

例如：

```
函数与极限章节测试
```

而不是：

```
帮我出一套第一章测试
```

---

# 3. TeachingDesign

## 3.1 创建条件

默认：

以下类型属于普通对话：

* 教学知识咨询。
* 学习建议。
* 方法讨论。

不创建 TeachingDesign。

只有用户明确需要可执行教学产物时，创建 TeachingDesign：

例如：

* 制定复习计划。
* 安排课程。
* 设计教学方案。
* 规划训练路径。

---

## 3.2 生命周期

流程：

```
用户提出教学设计需求
        ↓
创建 TeachingDesign
        ↓
展示给老师
        ↓
老师确认
        ↓
允许生成 Paper
```

规则：

* TeachingDesign 必须展示给老师。
* 老师确认后才能进入后续生成。
* Agent 不允许跳过确认直接生成试卷。

---

## 3.3 修改与版本

TeachingDesign 是长期存在、可修改的业务对象。

规则：

* 老师提出修改意见时，产生新的 TeachingDesign 版本。
* 保留旧版本。
* Paper 与生成时使用的 TeachingDesign 版本保持关联。
* 默认使用最新确认版本。

---

## 3.4 Conversation 隔离

* 新 Conversation 默认不继承旧 TeachingDesign。
* 老师明确提及历史方案时，可以 recall。
* 历史方案只能作为参考，不能覆盖当前任务约束。

---

# 4. Paper

## 4.1 创建关系

规则：

* 一个 Conversation 可以有多个 Paper。
* 一个 TeachingDesign 可以关联多个 Paper。
* Paper 可以没有 TeachingDesign。

---

## 4.2 Paper 修改

以下操作：

* 换第3题。
* 删除某题。
* 调整当前卷。

表示修改已有 Paper。

用户必须明确引用目标 Paper。

不允许：

* Agent 自动猜测 Paper。
* 默认使用最近 Paper。
* 默认使用 active Paper。

---

## 4.3 新建 Paper

以下请求：

* 重新出一套。
* 再出一套类似的。

创建新的 Paper。

---

## 4.4 Paper Version

Paper Version 是内部状态管理机制。

用途：

* 数据一致性。
* 回滚。
* 审计。

不是用户侧复杂版本树。

---

# 5. Question

## 5.1 数据来源

题目内容以审核后的题库内容为准。

规则：

* `reference_solution` 统一表示答案和解析。
* 不拆分为 Answer / Solution 两套业务概念。

---

## 5.2 Paper Snapshot

Paper 保存 Question snapshot。

规则：

* 历史 Paper 不受题库修改影响。
* 题库修正后，新生成 Paper 使用新内容。
* OCR 错误由题库管理界面人工修改。
* Agent 不负责自动修题。

---

## 5.3 禁止行为

生成 Paper 时：

禁止 LLM：

* 修改题干。
* 修改数字。
* 修改解析。
* 伪造新题。

---

# 6. Generation

## 6.1 约束原则

题库不足时：

禁止：

* 静默降低教师明确约束。
* 自动扩大章节范围。
* 自动降低题量。

应该：

* 明确告诉老师缺失原因。
* 给出可选调整方向。

如果老师明确接受调整：

例如：

```
那就出2道
```

再按照新约束生成。

---

## 6.2 Agent 可自动补充

Agent 可以提供默认：

* 教学目标。
* 默认难度。
* 默认题型配置。

因为这些属于软默认，可以在 Preview 中修改。

---

## 6.3 章节范围

章节范围属于硬约束。

规则：

* Agent 不能擅自决定章节归属。
* 存在章节歧义时必须请求确认。
* 历史 TeachingDesign 不能覆盖当前章节选择。

---

## 6.4 软约束与硬约束

硬约束：

* 章节范围。
* 题量。
* 题型限制。
* 分值要求。

软默认：

* 默认难度。
* 默认题型比例。
* 教学建议。

规则：

软约束可以提供默认值。

硬约束和业务范围不能自动扩大或缩小。

---

# 7. A/B Paper

## 7.1 定位

A/B 不是新的 Paper Entity 类型。

可以：

* 共享总体教学目标。
* 允许局部差异。

不要求两个 constraints 完全一致。

---

## 7.2 生成规则

B：

* 必须确定性排除 A 已使用 Question。
* 排重范围以当前 Conversation / 当前任务语境为主。
* 不做全局永久排重。

---

## 7.3 失败处理

如果：

```
A 成功
B 因题库不足失败
```

规则：

* A 必须保留。
* 告诉老师 B 失败原因。
* 老师可以补充题库后再次生成 B。
* 不允许偷偷降低硬约束。

B 依赖 A 成功生成。

---

# 8. 错题强化

规则：

* 排除原题本身。
* 可以使用相同知识点的其他题。
* 当前不实现复杂语义相似度去重。

---

# 9. Teacher Preference Memory

只保存老师明确表达的长期规则。

例如：

```
以后试卷默认100分
```

规则：

* 当前任务明确要求优先级最高。
* Preference 只作为默认值。
* 不覆盖当前任务明确约束。
* 老师明确修改长期偏好时覆盖旧 Preference。
* 不根据行为自动推断长期偏好。

优先级：

```
Current User Request
        >
Confirmed Task Constraint
        >
Teacher Preference Memory
        >
System Default
```

---

# 10. 总体状态原则

LLM 负责：

* 用户意图理解。
* 自然语言解析。
* 模糊语义提取。
* 解释和建议。

Python / Domain Service 负责：

* 业务规则。
* 状态流转。
* 约束验证。
* 数据一致性。
* Paper / TeachingDesign 生命周期。

业务事实以 Domain Entity 为准，不以 Conversation 内容或 LLM 输出为准。
